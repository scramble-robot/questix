# 走行制御リファクタリング計画: 路面変化へのロバスト化とチューニング性の改善

作成日: 2026-08-08
位置づけ: `design/drive_control_refactor.md`（PR #142 で Phase 0–3 実施済み）の続編。
同文書の Phase 4（車体速度閉ループ）を本計画の Phase C として引き継ぎ、その前段に
チューニング性のインフラ整備（Phase A/B）を挿入する。

## 0. 課題と方針

**課題**: スティック操作から走行制御までの経路で、路面が違うと制御品質が落ち、
再チューニングの作業性も悪い。

**方針**（検討の結果確定）:

- 路面ごとのパラメータプロファイル切替は**採用しない**。プロファイルは路面の数だけ
  手チューニングを増やす対症療法であり、切替忘れ・管理コストも生む。代わりに
  **運動モデルに基づく制御**（モデルベース PI + フィードフォワード + 外乱オブザーバ）で
  路面差を「外乱として推定し自動補償」する。ゲインは同定した物理モデルから導出し、
  「ノブ回し」を「物理パラメータ数個の同定」に置き換える。
- 制御 tick と観測レートは両方引き上げる。tick はシリアルから分離してバスより
  高周期にしてよい（tick > 観測レート）。ただし**すべての周期設計値はボーレート
  57600 起点の帯域計算から導出する**（§4）。
- config の多重化（デフォルト三重管理・installed コピー乖離・死んだキー）は解消し、
  「触るファイルは 1 つ、値の出所は YAML 唯一」にする。

## 1. 問題の分解

課題は独立した 3 つの欠陥に分解できる。対策はこの分解に対応する。

| # | 欠陥 | 本質 | 対応 |
|---|---|---|---|
| D1 | 補償機構の不在 | 車体速度 (v, ω) の閉ループが無い。`/odom` は publish されるが制御に未接続。路面の転がり抵抗変化がそのまま追従誤差になる | Phase C（本命） |
| D2 | チューニング作業の摩擦 | 加速整形 7 機構の非直交、config 反映経路の破損、不誠実な param callback、観測バイアス | Phase A/B（**実装済み**） |
| D3 | ファーム速度ループの低RPM不安定 | 旋回指令域の 84% が実測不安定域（1.8Hz 振動）。ホスト側平滑化では原理的に治らない | Phase C-2b / C-4 |

### 正直な限界（先に明記する）

- **スリップは観測できない**。フィードバックはモータ軸速度であり、車輪エンコーダ
  ベースの `/odom` はホイールスリップを見えない。Phase C の閉ループが除去できるのは
  転がり抵抗・負荷変化による追従誤差であり、滑る路面でのスリップそのものではない
  （スリップ検知には IMU 等の追加センサが必要）。
- **M0602C ファームは変更不可**。ボーレートも仕様で 57600 固定
  （`M0602C_234_仕様書_日本語訳.md` L145）。ファーム速度ループの低RPM不安定は
  「回避」（電流モード / 動作点シフト）しかできない。

## 2. Phase A: 基盤修正 — ✅ 実装済み（本計画と同時に実施）

モデルベース化の前提となるインフラ。全項目実装・テスト済み。

### A1. config インストール経路の修正 ✅

- **問題**: `launcher/CMakeLists.txt` の `install(DIRECTORY config/ ...)` は YAML を
  **コピー**するため、`--symlink-install` でも install 先が更新されず、実機は編集元と
  約 6 項目乖離した古い `drive_component.yaml` で走行していた
  （`max_linear_accel` 1.0 vs 3.0、`brake_on_stop` true vs false、`accel_time` 100 vs 1 等）。
- **変更**: `ament_auto_package(INSTALL_TO_SHARE launch config)` へ統一
  （`motor_control_app` と同方式）。ビルド後の install 先が symlink になることを確認済み。
- **効果**: 「YAML を編集 → ノード再起動で反映」が初めて成立。以降の全チューニング・
  同定実験の前提。
- **注意**: 切替直後、実機の挙動が「ソース YAML の正しい値」に変わる。直近の実走で
  体感が変わったらこれが原因（正しい状態に戻っただけ）。

### A2. パラメータ衛生 ✅

- `joy_controller_params.yaml` の未宣言デッドキー 10 件（servo系・`right_stick_x_axis`）を削除。
- `joy_controller` の `declare_parameter` デフォルト 0.1 を YAML 実効値 2.0 / 6.0 に統一
  （20〜60 倍の乖離。YAML を渡さない起動経路だけほぼ動かない罠だった）。dual_stick 版も同様。
- `joy_controller/README.md` 全面改訂（実在しない turbo/精密モード・サーボ制御・
  `/cmd_vel` 記述を削除、実パラメータ表に差し替え）。
- `motor_control_lib/README.md` 全面改訂(実在しない UnifiedMotorController 等を削除)。
- `motor_control_app/README.md` 新設（全パラメータ表: 単位・効き・実行時変更可否・
  チューニングワークフロー）。

### A3. 誠実な param callback ✅

- **問題**: `drive_component` の `onParameterChange` は再初期化が必要な 15 パラメータ
  （`max_motor_rpm`, `control_rate`, `control_mode` 等）を journal WARN だけで
  success 返却していた。`ros2 param set` が「成功」と報告するのに何も変わらない。
  電流モード PI ゲインは黙殺（ハンドラなし）。
- **変更**: 再初期化系は**拒否 + 復旧手順つき理由**を返す（`auto_start` 等の
  constructor 時パラメータも含め 18 項目）。電流 PI 系 6 パラメータ
  （`current_kp/ki`, `max_current_amp`, `integral_limit_amp`,
  `current_zero_deadband_rpm`, `current_invert_measured`）は実行時反映に対応
  — Phase C-2b の実機ゲインチューニングの前提。
- **回帰**: `test_drive_param_policy`（ノードレベル 4 ケース）を新設。

### A4. 観測バイアスの解消 ✅

- **問題**: `/drive_status` の実測 RPM は `measured_lpf_tau_sec: 0.15`（fc≈1.06Hz）の
  ローパス済みで、ファーム速度ループの ~1.8Hz 振動を**約半分**に見せる（92ms 遅れ）。
  「rosbag で見える振動は実際の半分」の状態で B/C のチューニングを始めると全評価が汚染される。
- **変更**: `questix_msgs/MotorFeedback` に `velocity_rpm_raw`（フィルタ前生値）を追加し、
  `/drive_status` で常時 publish。制御（電流PI）はもともと生値を読むため制御側変更なし。
- **運用**: 振動解析・システム同定は `velocity_rpm_raw` を使う。

### A5. シリアル往復レイテンシ実測基盤 ✅

- `DdtMotorLib::sendFrameWithFeedback` に往復時間（書込開始→応答受信完了）の計測を追加。
  統計（EMA / max / タイムアウト率）を `getSerialLatencyStats()` で取得でき、
  deactivate 時に INFO ログへ出力。
- **用途**: §4 の周期引き上げ（タイムアウト短縮量・目標レート）は、この実測値で決める。
  M0602C の最小コマンド間隔（未確認、設計文書 §7-2）の同定も兼ねる。

## 3. Phase B: パラメータ直交化 — 削除フェーズ ✅ / 改名フェーズは未実施

### B1-kill. 死んだ加速整形機構の廃止 ✅

「加速の滑らかさ」を司る機構が 7 系統重複し、「1 つ触ると他の効き方が変わる」状態だった。
keep / kill 判定と実施結果:

| 機構 | 判定 | 根拠 |
|---|---|---|
| `max_linear_accel` / `max_angular_accel` | **keep（主レバー）** | 追従性の第一レバー |
| デマンド適応（`min_*_accel`, `accel_demand_ref_*`） | **kill ✅（コードごと削除）** | 実機評価で逆効果と確定（微小入力 0.52s→0.14s、前進整定 1.22s→0.78s、いずれも無効化で改善）。無効化状態で 4 パラメータ + 分岐コードが残置されていた |
| テーパー帯（`slew_taper_band_*`） | **keep** | ジャーク整形の唯一の担当に責務集約 |
| ファーム `accel_time` | **kill ✅（定数 1 に固定、パラメータ廃止）** | 実機で「1 超は高RPM直進を乱す」と確定済み。左右共有・前後/旋回分離不可でレバーとして機能しない。ホストとの二重加速プロファイル問題が消滅 |
| ファーム速度ループ自体 | keep（不可変） | 回避対象であってレバーではない |
| `min_command_rpm` + 停止ヒステリシス | **keep（安全機能に再分類）** | ファーム不安定域への防波堤。チューニングレバーではない |
| `stop_resend_interval_ms` / `brake_on_stop` | **keep（停止挙動グループに隔離）** | 実機確定値（300 / false）。加速整形と無関係 |

結果、チューニング面は **入力 2（joy の入力比）+ 応答 4（max_accel×2 + taper×2）+
不感帯 1** に整理された。`test_control_core`（15 ケース）で指令列の回帰を確認済み。

### B1-rename. 改名フェーズ（未実施・別PR推奨）

- `longitudinal_input_ratio` → `max_linear_vel` [m/s]、`angular_input_ratio` →
  `max_angular_vel` [rad/s] など、「ratio」という名前が実態（フルスティック時最高速）と
  不一致な入力系の改名。
- **メリット**: 単位が明確になり、Phase C のモデルベース設計（速度指令の物理量扱い）と整合。
- **デメリット**: 運用者の手順・記憶を壊す。AGENTS.md ルールで .cpp/.hpp/yaml/launch/README
  同時更新が必要。移行期間は旧名 declare + WARN のエイリアスを検討。
- 工数 S–M。**Phase C 着手前に済ませるのが望ましい**（C のゲイン類を増やす前に名前空間を整える）。

### B3. 入力整形（未実施・任意）

- リスケール型 deadzone（現状はハードカットで微小入力の分解能が死んでいる）、
  expo カーブ（`out = (1−e)·x + e·x³`）、低速モードボタン。
- **メリット**: 微小旋回入力の指令が浅くなり、D3 の不安定域滞在時間が減る（運用上の緩和）。
- **デメリット**: 操縦者の再適応が必要。**根本対策ではない**。
- 工数 S–M。優先度は C より下。

## 4. 制御周期・観測レートの引き上げ（Phase C の帯域確保）

### 4.1 帯域予算（ボーレート起点で導出）

すべての周期設計値はここから導く。57600 baud / 8N1 = 5760 byte/s:

| 項目 | 値 | 根拠 |
|---|---|---|
| 1 byte | ≈ 173.6 µs | 10 bit/byte ÷ 5760 byte/s |
| 1 フレーム (10 byte) | ≈ 1.74 ms | Protocol 1 は指令・応答とも 10 byte |
| 1 往復/モータ | ≈ 3.5 ms + ファーム処理 | 送信 1.74 + 応答 1.74 + 処理（**A5 で実測する**） |
| 2 モータ直列 | ≈ 8 ms（名目） | 現行実装は同期直列 |
| **バス物理上限** | **≈ 100–125 Hz（両モータ）** | 8 ms/cycle。マージン込み実用 100 Hz |
| 現行 50 Hz の内訳 | 予算 20 ms のうち最悪 20 ms+ | 応答タイムアウト 10 ms ×2 が予算を支配 |

制約として明文化:

1. タイムアウト短縮の下限 = 応答フレーム伝送 1.74 ms + ファーム処理実測値 + マージン。
   それ未満には詰められない。
2. tick はバスより高くできるが、シリアル送信レートはバス上限を超えられない
   （tick 側は最新指令のみ送る。キューを溜めない）。
3. ホストループの交差周波数の上限は観測レート（= バスレート）で決まる
   （目安: 交差 ≤ 観測レートの 1/10。100 Hz 観測 → 交差 ~10 Hz が上限）。
4. モータ毎バス分離（C0-4）時のみ ~250 Hz/モータまで伸びる。

### 4.2 段階実装

| 段階 | 内容 | 工数 | 検証 |
|---|---|---|---|
| C0-1 ✅ | レイテンシ実測基盤（A5） | S | 実機で統計採取（要実走） |
| C0-2 | 同期構造のまま `control_rate` 100 Hz 化。応答タイムアウトを実測+マージンへ短縮 | S–M | 実機必須（指令レート倍増のファーム影響は §7-2 の未確認事項）。`test_control_core` のレート可変指令列一致テストで CI 回帰 |
| C0-3 | tick/シリアル分離: シリアルをワーカースレッド化しバス自然レート（~100–125 Hz）で連続トランザクション、ControlCore tick は 200 Hz+ で最新フィードバックスナップショット参照 | M–L | ループ遅延が「tick 周期 + 往復」→「往復のみ」に近づき、C-2b の位相余裕が改善 |
| C0-4 | モータ毎 UART バス分離（ハード追加） | L | C-2b の実験結果が更なる帯域を要求した場合のみ |

- C-2a（車体速度 PI トリム、交差 ~2 Hz 設計）は 50 Hz + ループ遅延 ~30 ms でも成立する
  （位相遅れ ~22°@2Hz）。C0-2 は安価なので先にやって損はない。
- C-2b（ホスト RPM ループ、交差 5–10 Hz 目標）は C0-2 が最低条件、C0-3 が推奨条件
  （50 Hz + 30 ms 遅延では 10 Hz で位相遅れ ~108° となり成立しない）。

## 5. Phase C: モデルベース制御（本命・未実施）

プロファイル無しで路面変化に対応する = 路面の違いを外乱として推定し自動補償する。

### C-1. システム同定（モデル取得）— 最初にやる

- **内容**: ステップ/チャープ応答の rosbag（A4 の `velocity_rpm_raw`）から車輪+車体の
  運動モデルを同定する。モデル候補: 一次遅れ + 負荷トルク項
  `J·dω/dt = K·u − B·ω − T_load`（T_load が路面抵抗に相当）。
  既存プラントモデル（`test_control_core.cpp` の一次遅れ + 1.8Hz 振動 + 量子化）を
  同定値で更新し、CI 上のチューニング環境を実機に近づける。
- **効果**: 以降の全ゲインをモデルから導出（極配置/ループ整形）できる。
  「ノブ回し」が「物理パラメータ 2–3 個の同定」に置き換わる — 路面が変わったら
  再同定 or 外乱推定に任せる、という原理的に閉じたワークフローになる。
- 工数 M。実機実験必須（異なる 2 路面以上で採取し、モデル差が T_load に吸収されることを確認）。

### C-2a. 車体速度 (v, ω) 閉ループ: モデルベース PI + FF + 外乱オブザーバ

- **構造**: `ControlCore` 内（純関数、シミュレーションテスト可能）に
  1. 逆モデルフィードフォワード（応答の主役。同定モデルから静的に導出）
  2. PI トリム（誤差補正。ゲインは極配置で導出、積分は モード遷移/停止/FB タイムアウトでリセット）
  3. 外乱オブザーバ（負荷トルク ≒ 路面抵抗をオンライン推定して打ち消す）
  を追加し、ファーム速度ループへの RPM 指令に加算する。
- **外乱オブザーバがプロファイルの代替**: 路面が変わっても推定外乱が変わるだけで、
  ゲインセットは 1 組のまま。これがユーザー要求（プロファイルを作らない）への直接回答。
- **メリット**: 路面訴求の本丸。転がり抵抗・負荷変化による追従誤差を自動補償。
  シミュレーション先行でゲイン初期値を CI 上で決めてから実機に持ち込める。
- **デメリット・リスク**:
  - スリップは補償できない（§1）。滑る路面では推定外乱が「滑り分を押し込む」方向に
    働き得るため、**トリム/補償量に上限**（`trim_limit_*`）を設けるのが防波堤。
  - 実測には 1.8Hz ファーム振動が乗る。オブザーバ帯域は振動より十分低く取る
    （でないと振動を「外乱」と誤認して増幅する）。
  - 外側ループが内側（ファーム）ループを励起しないゲイン上限をシミュレーションで先に当てる。
- 工数 M–L。依存: A4（生値観測）、C-1（モデル）。50 Hz のままでも成立（§4）。

### C-2b. 電流モード + ホスト側モデルベース速度制御（D3 の根治）

- **内容**: 既存の実験実装（`ddt_current_pi.cpp`、`control_mode: "current"`）を昇格。
  ファームの不安定な速度ループを完全バイパスし、ホストで RPM→電流ループを回す。
  電流 ∝ トルクなので運動方程式ベースの設計が正攻法になり、C-1 のモデルと
  外乱オブザーバがそのまま使える。
- **メリット**: 旋回指令域の 84% を占めるファーム不安定域の**唯一のソフトウェア的根治**。
  A3 でゲインが実行時変更可能になっており、実機チューニングの回転が速い。
  `control_mode` 1 つで velocity へ撤退可能（安全弁）。
- **デメリット・リスク**: ホストループ帯域は観測レートで頭打ち（§4.1 制約 3）。
  C0-2/C0-3 が前提。停止・E-stop 時の保持トルク挙動の再検証が必要。
- 工数 L。依存: A3・A5・C0-2（推奨 C0-3）・C-1。

### C-3. MPC の評価（選択肢として）

- **メリット**: 入力制約（加速度・RPM 上限）とモデルを一体で扱える。(v, ω) の
  カップリング考慮。Pi 5 なら 100 Hz の小規模 QP は計算可能。
- **デメリット**: 実装・保守コストが PI+FF+DOB より大幅に大きい。同定モデルの質に
  さらに敏感。この系（低次・制約単純・内側ループあり）では利得が薄い。
- **判断**: まず C-2a/C-2b。MPC は「軌道追従や制約処理が要件化した場合」の将来枠とし、
  C-2 の実機結果を見てから採否を決める（採用判断ゲート）。

### C-4. 動作点シフト（ハード選択肢）

- ギア比追加 / ホイール小径化で低RPM 不安定域を常用域から外す。制御の複雑さ増加ゼロ。
- 不可逆コストが大きいため、**C-2b の実験結果を待って判断**
  （電流モードで振動が消えるならハード変更不要）。

## 6. 実行順序

```
✅ A1 config経路 → ✅ A2 衛生 → ✅ A3 誠実callback → ✅ A4 生値観測 → ✅ A5 レイテンシ計測
→ ✅ B1-kill（7機構→直交セット）
→ [実機] A5 統計採取 → C0-2 100Hz化 → B1-rename → (B3 入力整形)
→ C-1 システム同定 → C-2a 車体速度 FF+PI+DOB → C0-3 tick/シリアル分離 → C-2b 電流モード
→ (C-3 MPC 判断) → (C-4 動作点判断)
```

順序原則:
1. **観測と config 経路を直してから制御を触る**（A4/A1 が C-1 の前提）— 済み。
2. 改名・直交化はモデルベース実装の前に（ゲイン類を増やす前に名前空間を整える）。
3. ソフト対策（C-2b）の結果を見てからハード変更（C-4）。
